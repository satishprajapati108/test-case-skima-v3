# playwright-session-kit

Reusable Playwright + TypeScript setup with persistent, multi-account login-session management. Chromium only. Ships with a working example suite against `app.staging.skima.ai` (jobs list + filters) on top of app-agnostic session/auth machinery.

---

## Project Structure

```
pages/        # Page Object Models — one file per major route
fixtures/     # Composable test fixtures (auth session injection, feature fixtures)
helpers/      # Env accessors, session path resolution, global auth setup
tests/        # Spec files — mirror pages/ structure
docs/         # Architecture diagrams for the auth/session flow
learn/        # Scratch TS exercises — not part of the suite, ignore when navigating features
.auth/        # Saved session state per SESSION_KEY (gitignored, generated by auth-setup)
```

## Environment Setup

Copy `.env.example` to `.env` and fill in values:

```bash
BASE_URL=https://app.staging.skima.ai
LOGIN_USERNAME=
LOGIN_PASSWORD=
SESSION_KEY=default
```

`BASE_URL` is required (`helpers/env.ts` throws if missing). `LOGIN_USERNAME`/`LOGIN_PASSWORD` are optional and only auto-fill the login form when **both** are set. `SESSION_KEY` namespaces `.auth/<key>.session.json` so different accounts/roles don't clobber each other's saved session.

## Running Tests

```bash
npm test                  # all tests, chromium
npm run test:ui           # visual UI mode
npm run test:debug        # step-through debug mode
npm run report            # open last HTML report
```

Or target a specific folder:
```bash
npx playwright test tests/jobs/
```

## Auth & Session Strategy

`helpers/auth-setup.ts` runs as Playwright's `globalSetup` once before the suite. On the first run for a given `SESSION_KEY` it opens a headed browser at `/login`, logs in (auto-filled if both credentials are set, manual otherwise), and saves the session to `.auth/<key>.session.json`. Every later run reuses that file.

`fixtures/auth.fixture.ts` overrides the built-in `context` fixture so every test gets a self-healing session: if the file already exists this is a fast read; if it doesn't (e.g. an IDE test runner skipped `globalSetup`), it runs the same login flow per-test instead of throwing `ENOENT`.

**Always import `test`/`expect` from `fixtures/` (or a fixture built on it), never from `@playwright/test` directly** — otherwise the session self-healing is bypassed.

To force re-login, delete the relevant `.auth/<key>.session.json` and run again.

## POM Rules

### Structure

- All POMs extend `BasePage` (`pages/base.page.ts`)
- One POM file per major route: `pages/<feature>/<feature>.page.ts`
- Group related locators and methods under a `// Section` comment (e.g. `//Search Job Locater`, `//Client Filter Logic`) so a long POM stays scannable by feature area
- Methods represent user actions or assertions grouped by the UI section they operate on (e.g. all "Client Filter" locators + `openClientFilter`/`filterbyClient` live together)

### Defining and accessing selectors

Declare locators as **class-level `readonly` properties**, not inline per-call — this repo's app exposes stable `data-testid` hooks for nearly every interactive element, so hoisting them lets every method in the POM reuse the same locator without re-querying:

```ts
export class JobsFilterPage extends BasePage {
  readonly search = this.page.getByTestId('jobs-search-input');
  readonly searchJobResultTable = this.page.getByTestId('jobs-table-row');

  async searchJob(jobName: string) {
    await this.search.fill(jobName);
  }
}
```

When several locators map to a named variant (tabs, statuses), define a `Record<Label, Locator>` map as a private class field next to the locators it's built from:

```ts
export type Label = 'All' | 'Draft' | 'NeedSetup' | 'ScoringOn';

private readonly tabmap: Record<Label, Locator> = {
  All: this.all,
  Draft: this.draft,
  NeedSetup: this.needSetup,
  ScoringOn: this.scoringOn,
};

async switchTotab(label: Label) {
  await this.tabmap[label].click();
}
```

### Selector priority

Prefer in this order:
1. `getByTestId` — the app exposes `data-testid` on interactive elements; it's the most resilient choice here and the default
2. `getByRole` — for generic elements without a testid (e.g. dropdown `option` roles)
3. `getByText` — for visible text, use `{ exact: true }` to avoid partial matches
4. `getByPlaceholder` / `locator('h1', { hasText })` — last resort, only when neither of the above applies

### Dropdown/filter panel pattern

Filter dropdowns in this app (status, ATS, client, location, etc.) follow a consistent open → wait → interact → apply shape. Reuse this pattern rather than inventing a new one per filter:

```ts
async openXFilter() {
  const isOpen = await this.xFilterOptions.first().isVisible().catch(() => false);
  if (!isOpen) {
    await this.xFilterOpen.click();
  }
  try {
    await this.xFilterOptions.first().waitFor({ state: 'visible', timeout: 5000 });
  } catch (e) {
    // options may legitimately be empty for this filter — caller checks count
  }
}

async filterByX(value: string) {
  await this.openXFilter();
  await this.page.getByText(value, { exact: true }).click();
  await this.xApplyButton.click();
}
```

### `goto()` must wait for real content

If a POM's route is navigated to directly (not via a fixture that already waits), `goto()` must wait for a visible landmark — not just `domcontentloaded`:

```ts
async goto() {
  await this.page.goto('/jobs');
  await this.searchJobResultTable.first().waitFor({ state: 'visible', timeout: 15000 });
}
```

## Fixture Rules

- `fixtures/index.ts` re-exports the base `test`/`expect` from `auth.fixture.ts` — this is the default import for specs that just need an authenticated page.
- For a feature used across many tests, add a **feature fixture** on top of the base one (see `fixtures/commons.fixture.ts`) that navigates to the route and hands back a ready POM instance, so specs don't repeat `new XPage(page)` + `page.goto(...)` in every test:

```ts
export const test = base.extend<{ jobFilterPage: JobsFilterPage }>({
  jobFilterPage: async ({ page }, use) => {
    await page.goto('/jobs');
    await use(new JobsFilterPage(page));
  },
});

export { expect } from './auth.fixture';
```

- Import from the most specific fixture file a spec needs (e.g. `fixtures/commons.fixture` for jobs specs), not `fixtures/index` + manual setup duplicated in the test.

## Spec Rules

### Structure

- Import `test` and `expect` from the appropriate fixture module (`../../fixtures` or a feature fixture like `../../fixtures/commons.fixture`) — never from `@playwright/test`
- Use `test.describe` to group tests by page or feature
- Destructure the feature fixture with a descriptive alias: `async ({ jobFilterPage: jobFilterObj }) => { ... }`
- Never call `page.locator()`, `page.getByRole()`, etc. directly in a spec file — always go through the POM

### Test naming

- Describe user behavior: `'should be able to filter jobs by status'`, not `'filter works'`
- Page load tests: `'<page> page loads'`

### Handling empty/variable data

Some filters (ATS status, client list) may have zero options depending on test data. Specs should read the option list from the POM first, `console.warn` and return early if empty, and otherwise iterate:

```ts
test('should be able to filter jobs by ATS status', async ({ jobFilterPage: jobFilterObj }) => {
  const atsStatusOptions = await jobFilterObj.getAtsFilterOptions();
  if (atsStatusOptions.length === 0) {
    console.warn('No ATS status filter options available. Skipping the test.');
    return;
  }
  for (const option of atsStatusOptions) {
    await jobFilterObj.filterByATSStatus(option);
  }
});
```

### Full spec example

```ts
// tests/jobs/job-filter.spec.ts
import { test, expect } from '../../fixtures/commons.fixture';
import { Label, statusMap } from '../../pages/jobs/jobs-filter.page';

test.describe('jobs filter', () => {
  test('should be able to switch between tabs', async ({ page, jobFilterPage: jobFilterObj }) => {
    const labels: Label[] = ['All', 'Draft', 'NeedSetup', 'ScoringOn'];

    for (const label of labels) {
      await jobFilterObj.switchTotab(label);
      const param = statusMap[label];
      const expectedUrl = param
        ? `${new URL(page.url()).origin}/jobs?by_status=${param}`
        : `${new URL(page.url()).origin}/jobs`;
      await expect(page).toHaveURL(expectedUrl);
    }
  });
});
```

## Adding a New Page

1. Create `pages/<feature>/<feature>.page.ts` — extend `BasePage`, declare `data-testid` locators as class-level `readonly` fields grouped by UI section, add action/assertion methods per section
2. If the feature is exercised across many specs, add a feature fixture to `fixtures/commons.fixture.ts` (or a new `fixtures/<feature>.fixture.ts` built on `auth.fixture`) that navigates and returns a ready POM instance
3. Create `tests/<feature>/<feature>.spec.ts` — import `test`/`expect` from the feature fixture (or `fixtures/`), group tests with `describe`
4. Start with a tab-switch/page-load test, then add filter/action-specific tests
